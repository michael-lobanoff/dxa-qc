# DXA QC — контроль качества денситометрических исследований

Сервис проверяет DICOM-снимки денситометрии (DXA) поясничного отдела позвоночника и проксимального
отдела бедра: пригоден ли снимок для интерпретации, и если нет — какое нарушение найдено и почему
(в градусах и миллиметрах). Работает локально, без обращения к внешним сервисам.

> Статус: решение собрано и проверено на всей выгрузке организаторов (499 файлов, 0 ошибок).
> Метрики, отрицательные результаты и ограничения — в `docs/night_report.md`.
> Лицензия — MIT ([LICENSE](LICENSE)). Медицинские данные организаторов в репозиторий не входят.

## Быстрая проверка решения

Нужен только Docker. Команды проверены на Linux и macOS.

```bash
git clone https://github.com/michael-lobanoff/dxa-qc.git && cd dxa-qc
./run.sh build                            # собрать образ, 5–10 минут, один раз
./run.sh check                            # проверить сборку — без медицинских данных
./run.sh predict /путь/к/исследованиям    # обработать папку или .zip → ./outputs
./run.sh serve                            # веб-интерфейс на http://localhost:8000
```

`./run.sh check` за десяток секунд убеждается, что образ рабочий: загружаются модели, конвейер
отрабатывает на синтетическом снимке, посторонние изображения отклоняются, таблица собирается
со всеми колонками ТЗ 2.5. Медицинские данные для этого не нужны.

**Что появится после `predict`:**

| Файл | Что внутри |
|---|---|
| `outputs/results.csv` и `.xlsx` | одна строка на изображение: область, проекция, вердикт, тип нарушения, измерения, время |
| `outputs/results_vis.zip` | по каждому снимку: PNG с подсветкой нарушения, DICOM Secondary Capture и DICOM SR |
| строка в консоли | `N images, N processed, 0 failed … mean time 0.43s` |

**Что стоит посмотреть в первую очередь:** колонку `quality_class` (0 — качественное, 1 — есть
нарушение), рядом `violation_type` со словами из словаря организаторов и `details` — измерения
в миллиметрах и градусах, по которым вынесен вердикт. Ошибки обработки не прерывают прогон:
такая строка получает `processing_status = Failure` и текст в колонке `error`.

Если Docker недоступен, то же самое запускается напрямую:

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt && .venv/bin/pip install -e .
.venv/bin/python scripts/selfcheck.py                                   # та же проверка сборки
.venv/bin/python scripts/predict.py /путь/к/исследованиям --out outputs/results.csv --vis outputs/vis
```

## Как это работает

```
DICOM → чтение и нормализация → область (позвоночник / левое / правое бедро)
      → ключевые точки (ансамбль из трёх U-Net) → измерения → решения по типам нарушений → строка отчёта
```

| Нарушение | Как определяется |
|---|---|
| Наклон оси позвоночника | угол линии «середина столба сверху — на уровне таза» к вертикали + тот же угол относительно линии гребней таза (наклон вместе с тазом — это укладка, наклон относительно таза — анатомия) |
| Некорректная укладка позвоночника | сеть не видит гребни подвздошных костей в кадре + доля яркой кости в нижних углах кадра (признак по пикселям, не зависит от аппарата); сверху — охват меньше 3.2 высот позвонка над линией гребней (ТЗ: до середины Th12) |
| Инородные тела | тонкие яркие структуры (top-hat) вне столба + сегментационная сеть |
| Поля вокруг области интереса бедра | расстояния от большого вертела (сверху), малого вертела (снизу) и наружного края вертела (сбоку) до краёв кадра, мм — как в ТЗ |
| Позиционирование / ротация бедра | HOG-признаки участка, выровненного по оси диафиза (ось прослеживается по кости), + ExtraTrees; ответы по кропам трёх детекторов усредняются |

Перед оценкой снимок проверяется на «свой/чужой»: пустой кадр, нерентгеновское изображение и снимок,
не похожий на денситометрию позвоночника или бедра, получают `quality_class 0`, код `unsupported`
и причину отказа вместо выдуманного вердикта (`dxaqc/region.py`). На 252 обучающих снимках отказов нет.

Каждый тип — маленькая монотонная модель по 1–3 измерениям с калибровкой и собственным порогом.

### Вердикт и рабочая точка

Снимок считается некачественным, если сработал **хотя бы один тип нарушения** — так каждый помеченный
снимок называет причину. Порог на общей вероятности вместо этого правила был опробован и отклонён
замером: после калибровки по процентилю объединение типов лучше по всем метрикам ТЗ 8.4 сразу
(F1 по снимкам 0.741 против 0.702, по исследованиям 0.800 против 0.752, macro-F1 0.611 против 0.588).
Общая вероятность собирается по областям по-разному: у позвоночника — из процентилей типов
(три типа по 6–17 нарушений, шкала вероятностей там неустойчива, AUC 0.856 против 0.845),
у бедра — из самих вероятностей (там доминирует ротация с 36 примерами, процентили её портят).
Потом одна калибровка на область сводит обе шкалы вместе — без неё общий AUC падает до 0.75.
Общая вероятность по-прежнему выводится в `quality_prob` — по ней считается ROC-AUC.

| Разрез | ROC-AUC | PR-AUC | F1 | Чувств. | Специф. | Сбал. точность |
|---|---|---|---|---|---|---|
| По снимкам (249) | 0.880 | 0.777 | 0.761 | 0.86 | 0.84 | 0.849 |
| По исследованиям (100) | 0.858 | 0.867 | 0.830 | 0.92 | 0.73 | 0.825 |
| Позвоночник (99) | 0.846 | 0.643 | 0.757 | 0.90 | 0.78 | 0.841 |
| Бёдра (150) | 0.905 | 0.832 | 0.764 | 0.83 | 0.87 | 0.850 |

По типам нарушений (AUC / F1 / число нарушений): инородные тела 0.914 / 0.801 / 17,
область интереса бедра 0.922 / 0.676 / 7, наклон оси 0.892 / 0.445 / 10,
ротация бедра 0.864 / 0.677 / 36, укладка позвоночника 0.847 / 0.715 / 6.
**macro-F1 по типам: 0.663.** Метрики локализации — `scripts/eval_localization.py`.

**Рабочая точка.** По умолчанию `balanced`: порог каждого типа выбран на максимум его F1 — именно при
нём измерены цифры выше. Для скрининга, где пропуск дороже ложной тревоги, есть вторая точка:
`DXAQC_POLICY=screening` (или выбор в веб-интерфейсе, или `?policy=screening` в API) ставит пороги на
чувствительность 0.80 по каждому типу и никогда не строже сбалансированных. Замер на той же
кросс-валидации: по снимкам чувствительность 0.86 → 0.92 ценой F1 0.761 → 0.710 и специфичности
0.84 → 0.73; по исследованиям чувствительность 0.92 → 0.94, F1 0.830 → 0.789.

Цифры получены на ансамбле из трёх детекторов точек, ни один из которых не участвовал в подборе
настроек: результат одного детектора зависит от случайной реализации (ротация бедра от 0.80 до 0.86
AUC при одинаковой ошибке точек), а ансамбль и выравнивание кропа по оси кости эту зависимость
убирают. Подробно — `docs/night_report.md`, раздел 21.

## Системные требования

Замер на 499 снимках (архив организаторов, MacBook M1 Pro, 24.09): только процессор — 0.43 с на снимок
(2.2 с на исследование, максимум 1.58 с на снимок), пик памяти 1.1 ГБ; с GPU (Apple MPS) — 0.13 с
(0.7 с на исследование), 0.7 ГБ.
Вердикты на CPU и GPU совпадают полностью. Время — в основном три детектора точек ансамбля; лимит ТЗ —
3 минуты на исследование. Модели — 141 МБ.

| | Минимальная | Рекомендуемая |
|---|---|---|
| CPU | 2 ядра x86-64 / arm64 | 4+ ядер |
| RAM | 2 ГБ | 4 ГБ |
| GPU | не нужен | любой CUDA-GPU (ускоряет в 2–3 раза) |
| Диск | 1 ГБ (CPU-сборка) | 6 ГБ (сборка с CUDA) |

Зависимости зафиксированы по версиям в [requirements.txt](requirements.txt); базовый образ —
`python:3.12.2-slim`. Основное: PyTorch 2.14 (CPU-сборка), OpenCV, scikit-learn, pydicom 3.0
с декодерами сжатых DICOM (pylibjpeg, pyjpegls), FastAPI + uvicorn, pandas, openpyxl, matplotlib.
Чужие предобученные веса не используются — все модели обучены на данных организаторов.

Устройство выбирается автоматически (CUDA → MPS → CPU); принудительно: `DXAQC_DEVICE=cpu|cuda|mps`.
Образ по умолчанию собирается с CPU-сборкой torch (она в восемь раз меньше, а лимит времени
перекрыт с запасом). Для хоста с видеокартой — тот же Dockerfile с другим индексом:
`docker build --build-arg TORCH_INDEX=https://download.pytorch.org/whl/cu124 -t dxa-qc .`
Повторный запуск на той же машине даёт идентичный результат. Между архитектурами (arm64 ↔ amd64)
отличается арифметика свёрток, поэтому вероятности слегка расходятся. Последняя сверка на всех
499 файлах архива: вердикт, типы нарушений, область и строка измерений совпали 499 из 499; вероятность
совпала до цифры у 328 снимков, расхождение больше 0.02 — у 13, максимальное 0.053.
Лимит ТЗ — 3 минуты на исследование; фактически — доли секунды.

Одним скриптом (нужен только Docker, проверено на Linux и macOS):

```bash
./run.sh build                    # собрать образ

./run.sh predict /path/to/studies # обработать исследования -> ./outputs
```

```bash
docker build --platform linux/amd64 -t dxa-qc .
docker run --rm -v /path/to/studies:/data -v $PWD/outputs:/out dxa-qc /data --out /out/results.csv --vis /out/vis
```

Без Docker:

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt && .venv/bin/pip install -e .
.venv/bin/python scripts/predict.py <папка_или_архив.zip> --out outputs/results.csv
```

## Веб-интерфейс и HTTP API

```bash
.venv/bin/uvicorn dxaqc.api:app --host 0.0.0.0 --port 8000
# затем http://localhost:8000 — загрузка файлов, таблица вердиктов, картинка по клику на строку
# в Docker: docker run --rm -p 8000:8000 -v /path/to/studies:/data -v $PWD/outputs:/out --entrypoint uvicorn dxa-qc dxaqc.api:app --host 0.0.0.0 --port 8000
```

| Метод | Что делает |
|---|---|
| `GET /` | веб-интерфейс: загрузка файлов, таблица, визуализация (ТЗ 2.6) |
| `GET /health` | статус и список загруженных моделей |
| `POST /predict?format=json\|csv\|xlsx\|zip` | multipart `files`: DICOM-файлы или один .zip; `zip` — таблица + визуализации |
| `POST /analyse` | то же, что `/predict`, но с картинкой в ответе — используется веб-интерфейсом |
| `POST /predict_folder` | `{"input": "/data", "output": "/out/results.csv", "vis": true}` — пакетная обработка смонтированной папки; пути только внутри `DXAQC_ALLOWED_ROOTS` (по умолчанию `/data`, `/out`, рабочая папка) |

Документация OpenAPI: `http://localhost:8000/docs`.

## Формат входных данных

На вход — исследования в DICOM без разметки: папка (в том числе с вложенными папками) или один
`.zip`. Одно исследование может состоять из одного-трёх изображений; снимки группируются по тегу
`StudyInstanceUID`.

Из метаданных используется только геометрия изображения: `PixelSpacing` / `ImagerPixelSpacing`,
а при их отсутствии — `Exposed Area` (0040,0303) с проверкой правдоподобия. Персональные данные
(имя, пол, возраст, дата рождения) не читаются и на решение не влияют — требование ТЗ 2.4.

Читаются несжатые DICOM и сжатые: JPEG Baseline и Extended, JPEG Lossless (Process 14 и 14 SV1),
JPEG-LS, JPEG 2000, RLE Lossless. Поддерживаются MONOCHROME1 (инвертируется), 16 бит (приводится
к 8 по перцентилям), RGB (переводится в оттенки серого) и многокадровые файлы (берётся первый кадр).

## Предобработка и постобработка

**Предобработка:** чтение пикселей → применение `RescaleSlope` / `RescaleIntercept` → инверсия для
MONOCHROME1 → приведение к 8 битам по перцентилям 0.5 и 99.5 → определение размера пикселя.
Для сети ключевых точек изображение дополняется до квадрата и масштабируется; левые бёдра
зеркалятся, чтобы сеть видела одну ориентацию, а координаты возвращаются обратно.

**Постобработка:** координаты точек переводятся обратно в пиксели исходного снимка, измерения
считаются в миллиметрах с учётом разного шага по осям, вероятности типов калибруются по процентилю
внутри обучающей выборки, вердикт собирается как «хотя бы один тип», а несовместимые сочетания
разрешаются правилами (например, на снимке с впечатанной разметкой аппарата инородные тела
не оцениваются).

## Формат результата

CSV (UTF-8 с BOM) и XLSX, одна строка на изображение. Формулировки нарушений, названия областей и
название колонки с вероятностью взяты из разъяснений организаторов (V2, вопросы 6, 8, 15):

- позвоночник: «Некорректная укладка», «Не выравнена ось позвоночника», «Присутствуют посторонние предметы»;
- бедро: «Некорректная укладка», «Некорректная область интереса»;
- сторона бедра в отчёте не указывается (определяется внутри — от неё зависит боковое поле).


| Колонка | Описание |
|---|---|
| path_to_study | папка исследования во входных данных |
| study_uid, image_uid | StudyInstanceUID, SOPInstanceUID |
| anatomical_region | «Поясничный отдел позвоночника» или «Проксимальный отдел бедра» |
| projection | «переднезадняя (AP)» — проекция исследования (ТЗ 2.2); пусто, если снимок не оценивался |
| quality_class | 0 — качественное, 1 — есть нарушение |
| violation_type | нарушения из закрытого списка через «; », пусто если нарушений нет |
| processing_status | Success / Failure |
| time_of_processing | секунды |
| quality_prob | вероятность нарушения в [0; 1] (для ROC-AUC) |
| violation_codes | коды нарушений (v_axis, v_pos, v_artifact, v_roi, v_posrot) или unsupported |
| details | измерения: наклон оси, охват в позвонках, поля кадра в мм; пометки (эндопротез, впечатанная разметка аппарата) |
| markup_suggestion | предложенная коррекция впечатанной разметки аппарата; подтверждается специалистом в веб-интерфейсе |
| mm_per_px, mm_per_px_source | размер пикселя и откуда он взят (`ExposedArea` / `default`) |
| error | текст ошибки для Failure |

## Известные ошибки и как они обрабатываются

Необработанных исключений нет: любая ошибка становится строкой отчёта со статусом `Failure`
и текстом в колонке `error` (ТЗ 2.7). Пакетная обработка при этом не останавливается.

| Что может случиться | Что делает сервис |
|---|---|
| Файл не читается как DICOM, битый или обрезанный | строка `Failure`, тип исключения и сообщение в `error` |
| В DICOM нет пикселей (только метаданные) | строка `Failure` с пояснением |
| Изображение не похоже на денситометрию (обычный рентген, пустой кадр, другая анатомия) | `processing_status = Success`, `quality_class = 0`, код `unsupported`, причина в `details` — вердикт не выдумывается |
| Размер пикселя в теге неправдоподобен для денситометрии (< 0.30 мм) | снимок отклоняется как не-денситометрия с указанием измеренного размера |
| Тега размера пикселя нет вовсе | берётся значение по умолчанию 0.6 мм, источник указывается в `mm_per_px_source` |
| Сеть не нашла анатомическую структуру (обрезана краем кадра) | соответствующее измерение выводится как «—», а не подменяется числом; тип нарушения при этом срабатывает |
| На снимке впечатана разметка аппарата | инородные тела не оцениваются (линии рамок неотличимы от металла), в `details` стоит пометка |
| Файл-дубликат или служебный файл macOS (`._имя`) во входной папке | пропускается |

Ограничения, которые не являются ошибками (один аппарат в обучении, редкие типы нарушений,
сколиоз, эндопротезы), перечислены ниже в разделе «Известные ограничения».

## Воспроизведение обучения

Полный порядок с ансамблем детекторов — в [docs/training.md](docs/training.md). Кратко:

```bash
python scripts/build_index.py                    # индекс снимков и меток, дедупликация
python scripts/train_region.py                   # классификатор области + проверка «свой/чужой»
for r in spine hip; do                           # три члена ансамбля детектора точек
  python scripts/train_keypoints.py --region $r --aug fix    --seed 100 --tag fix_s100
  python scripts/train_keypoints.py --region $r --aug strong --seed 100 --tag strong_s100 --epochs 200
  python scripts/train_keypoints.py --region $r --aug base   --seed 100 --tag base_s100
done
python scripts/ensemble_oof.py --tags fix_s100 strong_s100 base_s100 --out ens3
python scripts/synth_decision.py --tags fix_s100 strong_s100 base_s100 --name ens3 --no-eval
python scripts/fit_decision.py  --synth ens3 --members fix_s100 strong_s100 base_s100
python scripts/eval_pipeline.py --synth ens3 --members fix_s100 strong_s100 base_s100
```

Разметка точек: `data/train/keypoints.json` (схема — `docs/annotation_scheme.md`).

## Проверка на внешних данных

`python scripts/check_external.py data/external/mendeley_dexa_spine` — прогон по открытому набору
DXA-снимков позвоночника с другого аппарата (Mendeley Data, CC BY 4.0). Результат: область определена
верно на 342 из 342, защита «свой/чужой» не отклонила ни одного настоящего снимка, ложные
срабатывания по инородным телам — 1 % после вычитания впечатанной разметки аппарата (было 100 %).

`python scripts/check_markup_external.py data/external/mendeley_dexa_spine` — чтение и оценка
впечатанной разметки аппарата (дополнительный функционал ТЗ 2.6). На этом наборе рамки есть на всех
снимках: прочитаны на 139 из 174, отклонение разделителей аппарата от межпозвонкового промежутка —
медиана 1.8 мм; коррекция предложена на 2 снимках. У организаторов впечатанной разметки нет ни на одном
снимке, поэтому проверить её там нечем (см. `docs/night_report.md`, раздел 26).

Вторая проверка — на обычных рентгенограммах поясничного отдела (LUMOS, Zenodo, CC BY-NC 4.0):
это не денситометрия, и сервис должен отказываться их оценивать. Отказывает 66 из 66 —
по размеру пикселя из DICOM (< 0.30 мм) и по размеру изображения (> 1200 пикселей).

## Перенос на другой аппарат — что измерено

На внешнем наборе с чужого денситометра нет меток качества, поэтому их сделали конструктивно: вносим
в снимок нарушение по правилу ТЗ тем же генератором, что и для обучения, и смотрим, называет ли сервис
нужный тип (`scripts/check_synth_external.py`, 50 снимков).

| Внесено | Поймано |
|---|---|
| наклон оси больше 5° | 98 % |
| гребни ушли из кадра | 38 % (было 22 % до признака по пикселям) |
| нарисована косточка белья | вероятность типа сработала на 50 из 50, но в вердикт не идёт: на этих снимках впечатана разметка аппарата, и инородные тела на них не оцениваются |

Фон (сервис считает исходный чужой снимок некачественным) — 18 %, в основном по укладке: у другого
аппарата другое кадрирование, а наши пороги калиброваны на выгрузке организаторов. Если сервис
переносят на другой парк техники, пороги нужно перекалибровать на его снимках — это первое, что
придётся сделать.

## Известные ограничения

- Обучено на 100 исследованиях одного аппарата (GE Lunar Prodigy Advance).
- Размер пикселя: тега PixelSpacing нет, берётся из Exposed Area (0040,0303) — 0.60 по X и 0.606 по Y.
  Организаторы называют 1.05 мм по Y и 0.6 по X (разъяснения V2, вопрос 1); на выгруженных снимках это
  не подтверждается тремя независимыми измерениями (см. `dxaqc/pixels.py`), поэтому по умолчанию берётся
  тег, а переключение — одной переменной: `DXAQC_PIXEL_MM="0.6,1.05"`. На вердикт это почти не влияет:
  все пороги выучены на метках эксперта и подстраиваются под тот масштаб, в котором он смотрел снимки.
  Там, где в теге записана площадь всего стола (104 снимка из 252), берётся 0.607 мм/пикс.
- Бёдра с эндопротезом оцениваются как обычные (решение организаторов, Q&A 17.09), в `details` — пометка «эндопротез».
  В обучающих данных такие бёдра не размечены, поэтому качество на них не измерено.
- «Сколиоз» без типа нарушения в разметке эксперта сервисом не выявляется.
- Предложение областей измерения L1–L4 (ТЗ 2.6) проверено только на выгрузках организаторов.
  На публичном наборе с другого аппарата, где рамки напечатаны на снимке, шаг позвонков совпал,
  а фаза — нет, поэтому там предложение областей использовать нельзя (см. `docs/night_report.md`).
- Снимки с впечатанной разметкой аппарата: линии рамок вычитаются, оценка инородных тел на таких
  снимках не проводится (сервис об этом пишет), а сама разметка читается и проверяется — если
  разделитель уровней стоит дальше 4 мм от межпозвонкового промежутка, сервис предлагает, куда его
  сдвинуть. Проверено только на внешнем наборе: у организаторов такой разметки нет. На уменьшенных копиях (224×224) распознавание
  впечатанной разметки деградирует — сервис рассчитан на выгрузки в исходном разрешении.
- Верхний охват позвоночника (Th12) — в обучающих данных нет ни одного подтверждённого нарушения этого типа,
  поэтому правило намеренно консервативно: срабатывает только при охвате меньше 3.2 высот позвонка
  (у всех наших снимков 3.5 и больше).
- Уровни позвонков не нумеруются: на DXA без рёбер нумерация неоднозначна. Ось строится по двум точкам —
  ось по средним линиям позвонков оказалась заметно хуже (AUC 0.57 против 0.89).
