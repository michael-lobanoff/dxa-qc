# Ночной отчёт 15→16 сентября

**Коротко.** Готов работающий черновик сервиса целиком: DICOM → область → точки → 5 типов нарушений →
CSV/XLSX в формате ТЗ + картинки, DICOM SC и DICOM SR. Есть CLI, HTTP API, 11 тестов, README, Dockerfile
(не собран). Честная оценка (кросс-валидация по пациентам, все компоненты не видели снимок):
**ROC-AUC 0.83 [0.76–0.88], F1 0.63** по 249 снимкам. Сеть ротации бедра: лучший подход — HOG + случайный лес,
**AUC 0.81**; нейросети (обычная и многозадачная) хуже на 150 снимках. 0.05–0.13 с на снимок.

**Нужны твои решения:** (1) собрать Docker-образ — нужна загрузка базового образа; (2) пороги — максимум F1 или
выше чувствительность; (3) как выводить эндопротезы — ждём организаторов; (4) завести git-репозиторий в `lct`
(сейчас git видит весь домашний каталог) / SourceCraft.

Все метрики получены на кросс-валидации с разбиением **по пациентам** (исследования одного пациента
никогда не попадают одновременно в обучение и проверку). Для каждой части сервиса проверка «честная»:
точки берутся от детектора, не видевшего снимок, модель ротации тоже не видела снимок.

## 2. Ротация / позиционирование бедра (метка эксперта, 36 нарушений из 150)

| Подход | AUC (честно, точки от детектора) |
|---|---|
| Геометрия по точкам | ≈ 0.61–0.72 |
| Профиль внутреннего контура | 0.58 |
| HOG + логистическая регрессия | 0.67 |
| **HOG + случайный лес** | **0.81** (95 % ДИ 0.74–0.90) |
| HOG + градиентный бустинг | 0.79 |
| Маленькая CNN с нуля | 0.73 |
| CNN + бустинг (ансамбль) | 0.80 |
| Многозадачная сеть (точки + ротация) | 0.69 (0.59–0.81) — не помогла |

HOG — гистограммы направлений краёв на участке бедра, выровненном по точкам (диафиз вертикально,
одинаковый масштаб). Самая информативная зона — вокруг малого вертела, как и в клиническом критерии.
Лучший результат выбран по одним разбиениям и подтверждён на свежих (0.77–0.81), оценка честная:
участки для проверки вырезаны по точкам детектора, а не по ручной разметке.

Что не помогло: сети с нуля (обычная 0.73, многозадачная 0.69 — на 150 снимках их признаки не лучше HOG),
аугментация сдвигами участка (0.81 → 0.81), учёт второго бедра того же пациента (+0.003).
В сервисе — **HOG + случайный лес**. Графики: `docs/figures/rotation_approaches.png`.

## 3. Инородные тела на позвоночнике (17 из 99)

Металл — тонкие очень яркие структуры. Морфологический top-hat + компоненты вне позвоночного столба:
одна величина «площадь тонких ярких структур в верхних 40 % снимка» даёт AUC 0.90 без обучения;
в составе сервиса AUC 0.85. Ошибки: вертикальная клипса вплотную к позвоночнику (085), крючки (047);
в двух «ложных» срабатываниях эксперт не отметил видимые косточки белья (079, 037).

Сегментационная сеть металла (`scripts/train_artifact_seg.py`, `models/artifact_seg.pt`): учится на моих
рамках (23 снимка) + **синтетических** косточках, крючках и клипсах, нарисованных генератором на чистых снимках.
AUC 0.89, в паре с правилом 0.91 (95 % ДИ 0.80–0.99). Главная польза — попиксельный контур металла для показа врачу.

## 4. Сервис целиком — черновик работает

`python scripts/predict.py <папка|zip> --out outputs/results.csv` → CSV + XLSX, одна строка на изображение
в формате ТЗ (+ вероятность, коды нарушений, пояснение в мм/градусах). Ошибки → строка Failure.
Цепочка: чтение DICOM (MONOCHROME1, 16 бит, RGB, мультикадр) → область по содержимому
(классификатор, 252/252 и 3/3 тестовых файла) → точки → измерения → решения по типам нарушений.
Время ≈ 0.2–1.2 с на снимок. Тестовые файлы организаторов: `outputs/test_sample.csv`.

### Разбор ошибок (`docs/night/errors_*.png`)

- **Наклон оси:** все 4 самых уверенных ложных срабатывания — сколиоз (по комментарию эксперта). Эксперт не считает
  изогнутый позвоночник нарушением укладки. Добавлен признак **кривизны** (отклонение середины столба от прямой

- **Ротация:** системной ошибки не видно; два ложных срабатывания — очень короткие снимки с обрезанным диафизом (074).

## 7. 16 сентября: масштаб снимка и позвонки

### Нашли настоящий размер пикселя — раньше ошибались на треть

Мы считали 0.8 мм/пиксель «по анатомии на глаз». В DICOM-тегах нашёлся **Exposed Area (0040,0303)** —
размер снятой области в мм. У позвоночника это 180 мм на 300 пикселей, у бедра 170–180 мм на 280, то есть
**0.60–0.64 мм/пиксель**. Значение берётся из тега для каждого снимка (148 из 252); в части исследований
в теге записана площадь всего стола (520 мм, одна и та же для всех снимков исследования) — такие значения
отбрасываются проверкой правдоподобия, для них берётся 0.607 мм.

Две независимые анатомические «линейки» подтверждают тег: шаг позвонков (тело + диск) 50 пикселей → **30 мм**
и диаметр головки бедра 66 пикселей → **40 мм**. Оба значения нормальны для пожилых пациентов денситометрии.

Что это меняет: все расстояния в отчёте раньше были завышены на треть (поле «45 мм» на самом деле 34 мм).
Метрики не изменились — масштаб монотонный, ранжирование прежнее (ROC-AUC 0.825 [0.76–0.88], F1 0.63),
но миллиметры в отчёте врачу и в правилах ТЗ теперь настоящие. Заодно исчезло ограничение
«размер пикселя не откалиброван».

### Позвонки: что получилось и что нет

Проверяли идею размечать каждый позвонок. Нашли столб позвонков автоматически: вдоль оси тела позвонков
выглядят как тёмные блоки между яркими замыкательными пластинками (внутри тела кость менее плотная),
и эта «гребёнка» устойчиво ловится согласованным фильтром с априором регулярности (`dxaqc/vertebrae.py`,
9 мс на снимок).

- **Не помогло:** ось по средним линиям позвонков заметно хуже нашей оси по двум точкам —
  AUC 0.57 против **0.89**. На таком разрешении боковой центр отдельного позвонка гуляет на 10–20 пикселей
  (мешают суставные отростки, рёбра и таз), и наклон тонет в этом шуме. Вывод: ось оставляем как есть,
  отдельную сеть на позвонки не учим и 99 снимков заново не размечаем.
- **Помогло:** шаг позвонков — это «линейка» самого пациента. Критерий ТЗ «сверху должна быть видна
  половина тела Th12» мы раньше не могли проверить (правило в мм не было откалибровано). Теперь считаем
  охват **в позвонках**: от линии гребней до верхнего края нужно ~4.5 позвонка. На наших данных этот запас
  3.5–7.1 (медиана 5.1), нарушений такого типа эксперт не отмечал, поэтому правило срабатывает только
  при явной нехватке (< 3.2 позвонка) — чтобы не плодить ложные тревоги, но закрыть критерий ТЗ.
- Шаг устойчив: по точкам детектора и по ручным точкам он совпадает с медианной разницей 0.3 мм
  (88 % снимков — в пределах 2 мм).
- Уровни (L1, L2 …) сознательно **не называем**: без рёбер на DXA нумерация неоднозначна (межгребневая линия
  проходит то через L4, то через диск L4/L5), а ошибиться на уровень в медицинском отчёте хуже, чем не называть.
- На картинке врачу позвонки теперь отмечены, в заголовке — «над гребнями 5.1 позвонка (30 мм каждый)».

## 8. Рабочая точка: как ставим порог

Порог не влияет на ROC-AUC, но влияет на F1, чувствительность и специфичность — а ТЗ (8.4) считает всё
это. Сравнили политики честно: порог выбирается на одних исследованиях, метрика меряется на других
(`scripts/threshold_policy.py`).

| Как ставим вердикт | F1 | Чувств. | Специф. |
|---|---|---|---|
| было: «сработал хотя бы один тип» | 0.629 | 0.62 | 0.86 |
| порог по общей вероятности, максимум F1 | 0.627 | 0.76 | 0.72 |
| **порог по общей вероятности, цель чувствительность 0.80** | **0.642** | **0.82** | 0.69 |
| пороги по каждому типу с целью 0.8, «сработал тип» | 0.49–0.60 | 0.86–0.94 | 0.10–0.61 |

Выбрали третий вариант и поставили его по умолчанию (`DXAQC_POLICY=screening`, альтернатива `balanced`).
Почему:

- он лучше по **F1** — главной метрике ТЗ — и по сбалансированной точности (0.758 против 0.737);
- чувствительность 0.62 → 0.82: для контроля качества пропущенный брак дороже лишней проверки, лаборант
  видит картинку с подсветкой и тратит секунды;
- «сработал хотя бы один тип» наследует нестабильность сразу всех порогов: при 6–36 нарушениях на тип
  порог прыгает от фолда к фолду. Цель по чувствительности выбирает ту же область кривой стабильнее.

Цена: специфичность 0.86 → 0.69, то есть примерно каждое третье нормальное исследование получает пометку.
Если на питче скажут, что это много, переключение — одна переменная окружения.

Побочный эффект: 28 % помеченных позвоночников и 50 % бёдер не имеют типа, перешедшего свой порог.
Для них указывается наиболее вероятная причина и пометка «тип указан как наиболее вероятный» —
лаборанту нужно знать, что перепроверять, а строка «нарушение без типа» бесполезна.

## 10. Ответы организаторов: что поменяли (16 сентября)

- **«В итогах агрегации есть косяки, ориентируйтесь на столбцы конкретных нарушений».** Метка снимка
  теперь считается как «или» по типам нарушений, а не берётся из итогового столбца. Это перевернуло три
  строки: перелом (тип стоял, итог был «норма») и два сколиоза (итог «нарушение» без типа — сколиоз
  не является нарушением укладки). Метрики почти не изменились: F1 0.645, ROC-AUC 0.824.
- **«Столбец с вероятностью посчитают, если он есть».** У нас он есть с самого начала — `quality_score`.
  Ничего делать не нужно, но в сопроводительной записке стоит указать на него явно.
- **«Если сделаете защиту от чужих изображений — будет топ».** Сделали: перед оценкой снимок проверяется
  по трём признакам — пустой кадр, автокорреляция соседних пикселей (у любого рентгена ≥ 0.985,
  у шума 0.00) и расстояние в признаковом пространстве до ближайших обучающих снимков. Отклонённый
  снимок получает `quality_class 0`, код `unsupported` и причину. Проверено: из 252 обучающих снимков
  не отклонён ни один, а шум, пустой кадр, градиент, повёрнутый на 90° снимок и половина снимка
  отклоняются все. Сначала пробовали ошибку восстановления PCA — не годится: у белого шума
  «средняя» гистограмма направлений, и он восстанавливается лучше настоящей анатомии.
- **«Зона в тегах не указана, аппарат один, размеры одинаковые»** — наш способ определения области
  подтверждён; у нас он к тому же по содержимому картинки, а не по ширине (кросс-валидация 252/252).
- Ждём словарь формулировок нарушений и уточнённое ТЗ: будет **5 типов для бедра и 3 для позвоночника**
  (сейчас у нас 2 и 3). Разметка бедра сейчас содержит только два столбца, но часть недостающих
  критериев мы уже считаем правилами по точкам (видимость большого вертела, шейки, седалищной кости),
  так что коды добавятся без переобучения.

## 11. Сверка правил с клиническим стандартом

Нашли опубликованные рекомендации по контролю качества денситометрии (AJR 2011; Journal of Nuclear
Medicine Technology 2023). Наши правила им соответствуют, и появились две полезные детали:

- «Линия между верхними точками гребней подвздошных костей проходит через промежуток **L4–L5**» —
  это ровно то допущение, на котором построен наш пересчёт охвата в высоты позвонка. Теперь оно
  подкреплено источником, а не только нашей прикидкой.
- «Верхний край — часть нижнего грудного позвонка, **подтверждается наличием рёбер**» — совпадает
  с критерием ТЗ про половину Th12.
- Бедро: «вся головка, большой вертел и **не менее 2.5 см диафиза ниже малого вертела**» (в ТЗ — 3 см,
  оставляем как в ТЗ), «малый вертел едва виден», «**длинная ось бедра параллельна оси стола**».
- Последний критерий у нас не проверялся. Добавили измерение «ось бедра N° к вертикали» в отчёт.
  Отдельно он слабый (AUC 0.67 против метки ротации) и к модели ротации ничего не добавляет
  (0.806 против 0.804), поэтому в решающий слой не вошёл — но, вероятно, окажется одним из пяти
  типов нарушений бедра в новом словаре, и тогда измерение уже готово.

## 12. Разъяснения организаторов V2 (16 сентября)

Формат вывода приведён к их словарю:

- **violation_type** — закрытый список: позвоночник «Некорректная укладка» / «Не выравнена ось
  позвоночника» / «Присутствуют посторонние предметы»; бедро «Некорректная укладка» / «Некорректная
  область интереса». Несколько — через «; », при отсутствии поле пустое. Наши пять типов ложатся
  на этот список один в один (прежняя оценка «5 типов для бедра» не подтвердилась — их два).
- **quality_prob** — колонка вероятности, которую они посчитают. Переименовали (была `quality_score`).
- **anatomical_region** — только «Поясничный отдел позвоночника» и «Проксимальный отдел бедра»,
  сторона не важна. Сторону по-прежнему определяем внутри: от неё зависит, какое поле боковое.
- Суффиксов вроде `_ПОП` в именах файлов закрытого теста не будет — мы на них и не опирались,
  область определяется по содержимому снимка.

### Размер пикселя: расхождение, которое стоит уточнить

Организаторы: «1,05 мм по оси Y и 0,6 мм по оси X». По X совпадает с тем, что мы нашли в теге
Exposed Area. По Y — нет, и на выгруженных снимках 1.05 не подтверждается:

1. сам тег даёт 0.60 по X и 0.606 по Y на каждом снимке, где он описывает изображение;
2. **соотношение сторон позвонка**: ширина тела 64 пикс, шаг позвонков 50 пикс, отношение 1.28 —
   и поясничный позвонок действительно примерно в 1.3 раза шире, чем высота «тело + диск».
   При 0.6 × 1.05 он получился бы выше, чем шире, чего у человека не бывает;
3. абсолютные размеры при 0.6 нормальны (шаг позвонков 30 мм, головка бедра 40 мм), при 1.05 по Y —
   нет (52 мм и 69 мм);
4. если принудительно поставить 1.05, поиск позвонков перестаёт находить анатомически возможную
   цепочку и сваливается на удвоенную частоту («9.5 позвонка над гребнями» вместо 5.2).

Скорее всего 1.05 мм — это шаг строк сканирования до передискретизации при экспорте. Сервис теперь
поддерживает **разный масштаб по осям**: по умолчанию берётся тег, переключение — `DXAQC_PIXEL_MM="0.6,1.05"`.
На вердикт это почти не влияет, потому что пороги выучены на метках эксперта, а углы (наклон оси)
меряются на отображаемом снимке — в том виде, в каком эксперт и оценивал критерий «не более 5°».
**Вопрос организаторам:** относится ли 1,05 мм к выгруженным изображениям или к сырому шагу сканирования?

## 13. Проверка на внешних данных (350 снимков с другого аппарата)

Скачали открытый набор [Osteoporosis DEXA Scans Images of Spine from Pakistan](https://data.mendeley.com/datasets/9c2tz2xfyv/1)
(Mendeley Data, CC BY 4.0, больница Нистар, Мултан): 351 снимок денситометрии позвоночника с другого
аппарата, другой страны, в PNG без DICOM-тегов. Это первая проверка сервиса на данных, которых он
не видел ни в каком виде. Лежит в `data/external/` (в git не попадает), запуск — `scripts/check_external.py`.

**Что подтвердилось:**

- Определение области: **342 из 342 — «позвоночник»**, ни одной ошибки, хотя аппарат другой.
- Защита «свой/чужой» не отклонила ни одного настоящего снимка (новизна 0.85–1.02 при пороге 1.05).
- На снимках в исходном разрешении сервис даёт правдоподобную картину: 96 % «качественное»,
  4 % с нарушениями.

**Что сломалось и что починили.** На этих снимках впечатана собственная разметка денситометра —
рамки L1–L4 с подписями. Наш детектор инородных тел принимал эти линии за металл и помечал
нарушением **все 100 %** снимков. Добавили распознавание впечатанной графики: длинные строго прямые
линии вдоль осей кадра (у наших 252 снимков таких нет — медиана 0 на снимок, у внешних минимум 3).
Такие линии вычитаются из маски металла, а если их три и больше, сервис пишет «на снимке впечатана
разметка аппарата: инородные тела не оцениваются» вместо выдуманного нарушения. После правки ложные
срабатывания упали со 100 % до 1 %, а на данных организаторов ничего не изменилось (AUC инородных
тел 0.903 против 0.90).

**Граница применимости.** В том же наборе лежит копия, уменьшенная до 224×224 (квадрат, пропорции
искажены). На ней впечатанная разметка распознаётся только в 58 % случаев и ложные срабатывания
возвращаются (20 %). Вывод честный: сервис рассчитан на выгрузки в исходном разрешении, а не на
уменьшенные квадратные копии. На данных организаторов все снимки исходные.

**Ещё одно наблюдение.** Эти снимки — как раз пример того, что ТЗ называет «разметкой областей
измерения»: аппарат сам рисует рамки L1–L4. У организаторов таких нет, но это подсказка, как
выглядит вход для проверки чужой разметки, если её добавят.

## 14. Предложение областей измерения (ТЗ 2.6) — и его граница

Денситометр меряет плотность внутри рамок, которые ставит сам: L1–L4 на позвоночнике и область
шейки/вертелов на бедре. В выгрузках организаторов этих рамок нет, поэтому сервис **предлагает**,
где им быть: границы между телами позвонков берутся из цепочки позвонков, привязка по линии гребней
(по клиническим рекомендациям она проходит через промежуток L4–L5). На картинке это голубые
прямоугольники с подписями L1–L4; для бедра — одна рамка вокруг головки, вертелов и шейки.
Это именно предложение «с возможностью подтверждения специалистом», как и сформулировано в ТЗ.

**Проверили на внешних данных — и получили честный отрицательный результат.** На публичном наборе
из Пакистана денситометр напечатал свои рамки прямо на снимке, то есть там есть эталон. Сравнение
на 155 снимках: шаг позвонков наш и аппаратный совпадают (отношение 1.09), **а фаза — нет**:
распределение смещения наших границ относительно напечатанных практически равномерное
(медиана 0.26 при 0.5 = «ровно посередине»). То есть на снимках другого аппарата цепочка находит
структуру с правильным периодом, но не привязывается к тем же позвонкам.

Пробовали чинить автоматическим выбором полярности (тела темнее промежутков или наоборот) — не
помогло, расхождение даже выросло (17.9 → 22.1 пикс), поэтому переключатель убрали: лишняя сложность
без доказанной пользы.

**Вывод, который и пойдёт в презентацию:** предложение областей проверено только на выгрузках
организаторов (где цепочка подтверждена тремя независимыми способами — см. раздел 7); на другом
аппарате его использовать нельзя без повторной проверки. Это ограничение мы нашли сами, до жюри,
и именно так о нём и говорим.

## 15. Подтяжка моделей: что дало эффект, а что нет

Итог: **ROC-AUC 0.824 → 0.857, F1 0.645 → 0.674**, специфичность 0.69 → 0.77 при чувствительности 0.79.
Всё измерено одинаково: кросс-валидация по пациентам, признаки от детектора, не видевшего снимок.

### Сработало

| Что | Эффект |
|---|---|
| Калибровка по **процентилю** оценки вместо сырой шкалы | v_pos 0.758 → 0.878, всего +0.016 AUC |
| Инородные тела: **один признак** вместо трёх | AUC по фолдам 0.869 → 0.893, F1 0.681 → 0.709 |
| **Общий порог** вердикта вместо раздельных по областям | F1 0.636 → 0.656 |
| Ротация: **ближний план** шейки и малого вертела в признаках | 0.789 → 0.791 |
| Ротация: обучение **на кропах детектора** наравне с ручными | 0.791 → 0.807, разброс вдвое меньше |
| Ротация: **ExtraTrees** вместо случайного леса | 0.807 → 0.825 |
| Ротация: подмешивание **второго бедра того же пациента** | F1 типа 0.494 → 0.594 |

Про калибровку подробнее: Платт-сигмоида, подогнанная на 6–17 положительных примерах, в каждом фолде
получалась своей, и вероятности из разных фолдов оказывались в разных шкалах. Само ранжирование внутри
фолда было правильным — терялось именно при объединении и при noisy-OR по типам. Калибровка процентиля
решает это: шкала [0, 1] одинакова в любом фолде.

Про второе бедро: оба бедра укладывают в одну сессию, и метки ротации левого и правого совпадают
гораздо чаще случайного — корреляция 0.59, вероятность нарушения справа при нарушении слева 0.67
против базовых 0.24. Мы это раньше не использовали.

### Не сработало (проверено и отброшено)

- **Профиль медиального контура** — «выступ малого вертела», то самое, на что смотрит врач: AUC 0.52.
  Контур на этом разрешении не даёт устойчивого выступа.
- **Мелкая сетка HOG** (8 пикс) — 0.754 против 0.789; **PCA-сжатие** признаков — 0.70–0.74.
- **Бустинг и логистическая регрессия** вместо леса, ансамбли из них — не лучше.
- **Дрожание кропов** при обучении — 0.811 против 0.807 при большем разбросе.
- **Объединение типов через процентили** — лучше для позвоночника (+0.014), заметно хуже для бедра (−0.034).
- **Багированные пороги** и **выбор политики порога по типу внутри фолдов** — macro-F1 не растёт.
- **Второй признак для укладки позвоночника** (охват, расстояние гребней до края, их наклон) — ни один
  не улучшает уверенность сети в гребнях (0.878).

### Где потолок

Отдельно проверили, сколько теряется из-за неточности детектора точек: модель ротации, проверенная
на **ручных** кропах, даёт 0.789 против 0.825 на кропах детектора. То есть идеальный детектор ротации
не улучшил бы — вкладываться в него смысла нет. Для полей кадра бедра ручные точки лучше по нижнему
полю (0.927 против 0.860) и хуже по верхнему (0.792 против 0.857).

Оставшиеся ограничения — это число примеров: наклон оси 10 нарушений, укладка 6, поля кадра 7.
При таких количествах F1 по отдельным типам нестабилен по определению, и это видно по доверительным
интервалам.

## 16. Вторая внешняя проверка: настоящий рентген вместо денситометрии

Скачали [LUMOS](https://zenodo.org/records/18173664) (CC BY-NC 4.0): рентгенограммы поясничного отдела
в DICOM, 803 пациента, 1620 снимков, Philips DigitalDiagnost. Взяли подмножество — 66 снимков.
Это **не денситометрия**, а обычный рентген той же анатомии: самый честный тест для защиты
«свой/чужой», потому что похоже по анатомии и совершенно другое по природе.

**Сервис их принял.** 62 снимка из 66 были определены как «поясничный отдел позвоночника», получили
вердикт и измерения вида «наклон оси 18.5°, высота позвонка 28 мм». Проверка новизны не сработала:
она сравнивает HOG после приведения к 128×128, а там разница в разрешении исчезает.

**Починили двумя правилами с огромным запасом:**

| Признак | Наши DXA | DXA другого центра | Рентген LUMOS |
|---|---|---|---|
| Длинная сторона, пикс | 280–405 | 224–401 | 2335–3320 |
| Размер пикселя, мм | 0.60–0.65 | тега нет | 0.118–0.144 |

- если DICOM сообщает настоящий `PixelSpacing` меньше 0.30 мм — это рентген, а не денситометрия
  (у денситометра детектор идёт с шагом около 0.6 мм);
- если длинная сторона больше 1200 пикселей — то же самое, но работает и без тегов (для PNG).

После правки: рентген отклонён **66 из 66** с понятной причиной, DXA из Пакистана принят **350 из 350**,
наши 252 снимка — ни одного отказа. Побочный эффект: отказ происходит до анализа, поэтому чужой
снимок обрабатывается за 0.06 с вместо 1.5 с.

Ещё одна мелочь, которую дал этот набор: у них файлы с расширением `.Dcm`. Наш обходчик это переживает —
расширение приводится к нижнему регистру, а если его нет, проверяется сигнатура `DICM` внутри файла.

## 17. 17 сентября: предобученные сети и перебор описания (ротация 0.834 → 0.866)

Проверяли главную гипотезу — что предобученная на ImageNet сеть побьёт ручные признаки. **Не побила.**

| Подход | AUC |
|---|---|
| HOG + ExtraTrees (наше) | **0.825** |
| ResNet-18, признаки замороженной сети | 0.729 |
| ResNet-18, дообучены layer3–4 и голова | 0.788 |
| ResNet-18, дообучена вся сеть | 0.788 |

Признаки natural images плохо описывают форму кости, а 150 снимков мало для дообучения даже
с аугментацией. Веса скачивались с разрешения, лицензия позволяет; в решение они не вошли.

**Что ещё не сработало:** усреднение предсказания по 5 и 9 сдвинутым кропам на инференсе
(0.822 и 0.820 против 0.825); добавление геометрических признаков к HOG (0.825, ровно как без них).

**Ловушка, в которую я попал и из которой вылез.** Заметил, что наша собственная оценка размера
малого вертела (1 — едва виден, 2 — норма, 3 — крупный) размечена на всех 149 бёдрах, а нарушений
всего 35, и доля нарушений по оценкам U-образная: 27 % / 12 % / 69 %. Идея: учить промежуточную
цель — размер вертела, а из неё считать вероятность нарушения. Первый замер дал **0.876** против 0.825.
Но вес отображения я подобрал, посмотрев на таблицу по всем данным, то есть протащил ответ в модель.
Честные версии: вес подбирается внутри фолдов — **0.768**; отображение учится логистической
регрессией на честных входах — **0.665**. Идея мертва, цифра 0.876 была самообманом.

**Что сработало: систематический перебор описания кропа.** 20 сочетаний размера сетки HOG по всему
бедру и по ближнему плану. Победитель — крупная сетка (20 пикселей) по бедру плюс мелкая (6) по
ближнему плану шейки и вертела. Поскольку победитель из двадцати всегда смещён вверх, проверили на
зерновых значениях, на которых он не выбирался: **0.852 против 0.828** — тот же разрыв.

Итог: ротация 0.834 → **0.866**, бёдра 0.874 → **0.902**, общий ROC-AUC 0.857 → **0.870**,
F1 0.674 → **0.691**, специфичность 0.77 → 0.79.

**Разбор ошибок ротации.** Самые уверенные пропуски — это случаи, где вертел **не виден**
(переротация), а ловим мы уверенно обратное: крупный вертел при недоротации. Логично: «слишком
маленький вертел» и «нормальный вертел» отличаются тоньше, чем «нормальный» и «выпирающий».
Здесь и остался запас, если появятся новые размеченные данные.
