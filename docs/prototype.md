# Прототип: как запустить и что посмотреть

Прототип — веб-интерфейс и HTTP API поверх того же кода, что считает метрики. Разворачивается
одной командой на машине проверяющего и работает полностью офлайн.

## Почему нет ссылки на публичный стенд

ТЗ 3.2 требует обработки **«без передачи медицинских изображений во внешние системы»**. Публичный
стенд, куда загружают чужие снимки, этому требованию противоречит: изображения ушли бы на сторонний
сервер. Поэтому прототип поставляется образом, который поднимается у проверяющего: снимки не
покидают его машину, интернет при работе не нужен совсем.

## Запуск, три команды

```bash
git clone https://github.com/michael-lobanoff/dxa-qc.git && cd dxa-qc
./run.sh build      # собрать образ, 5–10 минут, один раз
./run.sh serve      # веб-интерфейс на http://localhost:8000
```

Без Docker то же самое:

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt && .venv/bin/pip install -e .
.venv/bin/uvicorn dxaqc.api:app --host 127.0.0.1 --port 8000
```

## Проверка, что сборка живая — без медицинских данных

```bash
./run.sh check
```

За десяток секунд проверяет четыре вещи: модели загружаются, конвейер отрабатывает на синтетическом
снимке, посторонние изображения отклоняются, таблица собирается со всеми колонками ТЗ 2.5.
Настоящие исследования для этого не нужны — это сделано ровно для того, чтобы работоспособность
можно было подтвердить до того, как под рукой окажутся данные.

## Что посмотреть в интерфейсе

Перетащите в окно DICOM-файлы, архив `.zip` с исследованием или то и другое вместе, нажмите
«Проверить».

1. **Сводка.** Сколько файлов, сколько с нарушениями, сколько качественных, по скольким оценка
   не проводилась, сколько не обработано, среднее время на снимок.
2. **Таблица.** По каждому снимку: анатомическая область, вердикт, тип нарушения словами из
   словаря организаторов и **измерения, по которым вердикт вынесен** — градусы и миллиметры.
   Проверяющему не нужно верить модели на слово: он видит ту же величину, по которой судит сам.
3. **Снимок с подсветкой** — по клику на строку. Красным обведено то, из-за чего снимок помечен
   некачественным; голубым — ключевые точки и предложенные зоны измерения; жёлтым — поля кадра.
   Соседние снимки листаются стрелками.
4. **Два режима.** «Сбалансированный» — рабочая точка по максимуму F1. «Скрининг» — ловит больше
   брака ценой ложных тревог; лаборатория выбирает сама.
5. **«Скачать CSV»** — тот же результат таблицей в формате ТЗ 2.5.

Сервис умеет отказываться: если на вход пришла не денситометрия, в вердикте будет
«не оценивался» и причина («размер пикселя 0.14 мм — это не денситометрия»), а не вердикт наугад.
Файл, который не читается как DICOM, тоже попадает в таблицу — строкой со статусом Failure
и причиной, чтобы ничего не терялось молча.

## Пакетная обработка и API

```bash
./run.sh predict /путь/к/исследованиям        # папка или .zip → ./outputs
```

На выходе `results.csv` и `.xlsx` в формате ТЗ 2.5, а с визуализацией — PNG с подсветкой,
DICOM Secondary Capture и DICOM SR по каждому снимку.

HTTP API: `GET /health`, `POST /predict` (json / csv / xlsx / zip), `POST /analyse`
(строки плюс картинка), `POST /predict_folder`. Swagger — на `http://localhost:8000/docs`,
спецификация лежит в [openapi.json](openapi.json) и открывается без запуска сервиса.
